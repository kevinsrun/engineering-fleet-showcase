# Current limitations and roadmap

This page describes the reviewed evidence checkpoint of November 1, 2026. Later uncommitted development is outside its acceptance scope.

## Operational acceptance is narrower than implementation

The latest completed full verification passed at private source `96545043d0e55127c6e0efcfd03ccfbd55b44110`. It is engineering verification, including deterministic and local fixtures. Positive authenticated live acceptance of that repaired runtime has not been established. Dispatch remains suspended at the reviewed checkpoint. Preparing this showcase did not authorize or initiate inference, resume execution, or alter provider permissions.

Historical native coding was demonstrated at older versions. A later historical result remained partial, with external consumption unknown. Neither historical success nor current test counts establish universal provider readiness.

## Parallel corps remain a goal

The four corps and project assignments in the architecture diagram are conceptual. No current simultaneous four-project execution, general worker-concurrency ceiling, or sustained multi-provider production throughput is claimed. Multiple adapters do not establish multiple eligible concurrent workers.

Provider entitlements, availability, task dependencies, shared resources, and review capacity constrain useful concurrency. Provider-internal workers are not assumed observable.

## Economic and productivity claims remain unproven

No general cost saving, token saving, human-attention improvement, or throughput advantage is established. The five-case historical comparison found greater Fleet latency. Its direct path included a deterministic application and verification harness; it was not an unrestricted interactive coding benchmark. Host conditions were not randomized, tasks were bounded, and interrupted usage was unknown.

## Verification has limits

Passing tests cover recorded checks at a particular source version. They do not prove defect absence, safe behavior under every environment, current authentication, or production suitability. Skipped checks stay visible. Focused test counts overlap full-suite counts. Independent deterministic verification means the coding worker did not define or modify its acceptance checks; it does not imply a separate human audit.

## Public reproducibility is deliberately limited

The public repository contains sanitized summaries and receipt hashes, not backend source, raw logs, private ledgers, prompts, or provider configuration. Readers can inspect arithmetic and trace public claims to summary identifiers, but cannot rerun private system verification from this showcase. Receipt hashes identify retained artifacts; they do not independently authenticate a claim without access to those artifacts.

## Next milestones

1. Complete a separately authorized live acceptance of the repaired runtime with independently checked outputs.
2. Demonstrate eligible concurrent workers on independent repositories, recording dependencies and whole-batch wall time.
3. Compare accepted outcomes, failures, retries, attributable consumption, and human intervention on matched tasks.
4. Measure how coordination and verification overhead scale as worker count grows.
5. Continue improving evidence freshness, handoff reliability, and operator visibility while preserving honest unknowns.

These milestones are planned work. This showcase creates no live dispatch authorization or production-readiness claim.
